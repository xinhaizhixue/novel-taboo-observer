## 1. 产品定义

### 1.1 一句话定义

**[已确认]** 一个以 Git 仓库承载作品、以本地写作工作台承载交互、通过桥接通用 Agent 完成绝大多数写作劳动的长篇网文创作系统。

作者打开一个小说项目后，可以直接写作，也可以把规划、续写、改写、审校、考据、状态维护、卡文诊断等工作交给 Agent；系统持续知道作品写到哪里、下一步做什么、有哪些风险。

**[已确认]** 最终创作方向和不可逆动作仍由作者决定或明确授权。

### 1.2 核心目标

**[已确认]** 产品目标不是只生成正文，而是尽可能覆盖一部长篇小说从构思到完结、修订和发布准备的完整工作。

**[已确认]** 自动化原则：

> 能让 AI 做的，坚决不让人重复做。

**[已确认]** 作者控制原则：AI 可以主动生成、推演和执行，但不得悄悄替作者确认不可逆的创作方向，也不得未经授权提交、推送或发布。

### 1.3 产品形态

**[已确认]**

- 产品是轻量、本地、编辑器中心的 AI 写作工作台，交互形态类似简化的 VS Code，但不是通用编程 IDE。
- 一个故事世界或系列作品使用一个 Git 仓库；独立小说可以视为只包含一本书的系列。
- 正文和重要创作资产由 Git 管理，作者可以通过 diff 查看人类和 Agent 的全部正文改动。
- 工作台负责编辑、展示、协调、权限和状态管理。
- 工作台不直接调用大模型 API，也不重新实现模型 Harness。
- 工作台桥接 Codex、Claude Code、Copilot、TraeX 等通用 Agent，复用它们已有的模型、上下文、工具、权限、Skills/MCP 和会话能力。
- 第一阶段作者正文格式只支持 Markdown 和纯文本。

### 1.4 产品不是什么

**[已确认]**

- 不是只做“续写一段”的聊天壳。
- 不是要求作者依赖仓库中的原始文本文件理解全部状态的纯命令行方案。
- 不是直接连接多个模型 API 的模型聚合平台。
- 不是替代 VS Code 的通用开发工具。

**[已确认]** 不是自动替作者确认故事价值、核心审美和最终发布的全自动流水线。

## 2. 目标用户与第一版边界

### 2.1 目标用户

**[已确认]** MVP 的主要用户是：

- 个人中文长篇网文作者；
- 在本地电脑创作；
- 愿意用 Git 管理作品，但不要求熟练掌握 Git 命令；
- 已安装并登录至少一个受支持的通用 Agent；
- 既可能自己写正文，也可能把部分正文交给 Agent；
- 希望系统持续维护大纲、设定、状态、任务和质量反馈。

### 2.2 第一版范围

**[已确认]**

- 本地打开一个小说/系列 Git 仓库；
- 编辑 Markdown、TXT 正文；
- Agent 直接修改正文文件，不设置单独草稿层；
- 作者通过编辑器和 Git diff 查看改动；
- Agent 可以自动维护进度和待办；
- 支持系列内多本作品的关联；
- 支持作者写作与 Agent 写作两种模式；
- 支持作者主动开启 Observer 会话，关闭后停止观察；
- 支持从开书到持续创作的智能引导。

### 2.3 第一版范围限制

**[已确认]**

- 单人作者，不做实时多人协同；
- 中文优先；
- 先完整支持一个主 Agent，再用第二个 Agent 验证适配协议；
- 先支持一个桌面操作系统，但数据格式和核心逻辑必须跨平台；
- 不依赖远程平台数据库才能恢复作品；
- 不做移动端正文编辑。

## 3. 核心概念

| 概念 | 定义 |
|---|---|
| 故事世界/系列仓库 | 一个 Git 仓库，包含一个共同世界下的一本或多本作品及其共享知识。 |
| 作品 | 系列中的一本小说。独立小说是系列中唯一的一本作品。 |
| 卷 / 章 / 场景 | 正文的层级结构；场景可以由显式标记或系统推断。 |
| Agent | Codex、Claude Code 等具备会话、工具和文件操作能力的通用智能体。 |
| 角色 | 注入给 Agent 的写作职责，如 Writer、Observer，不等同于特定模型。 |
| 创作导航器 | 根据作品阶段和故事状态组织当前目标、下一步和剧情路线的协调角色。 |
| Observer | 在作者主动开启的会话中观察人类或 Agent 的写作，提出评论并复查修改结果。 |
| 故事正典 | 已确认或有正文证据支持的世界、人物、时间线、知识边界和叙事承诺。 |
| 编辑器缓冲区 | 作者当前看到并编辑的内容，可能尚未保存到磁盘。 |
| 保存 | 把缓冲区写入 Markdown/TXT 文件，不等于 Git 提交。 |
| 恢复快照 | 用于崩溃恢复的临时副本，不等于正式保存或 Git 提交。 |
| Observer 快照 | Observer 开始分析时取得的不可变文本版本。 |
| 任务 | 有目标、执行者、范围、完成条件和状态的创作工作单元。 |
| 评论 | 锚定正文范围或作品对象的 Observer/Agent 建议线程。 |

## 4. 产品职责边界

### 4.1 工作台

**[已确认]** 工作台负责：

- Markdown/TXT 编辑与文件树；
- 作品、人物、设定、时间线、目标、任务的结构化展示；
- Agent 进程和会话生命周期；
- Agent 角色注入、任务分发和消息转发；
- 评论、反馈、通知和状态流转；
- 权限门禁和高风险动作确认；
- Git 状态、diff 和显式提交入口；
- 编辑缓冲区、磁盘文件、Agent 修改之间的冲突处理；
- 可重建索引和上下文包的组织。

### 4.2 通用 Agent

**[已确认]** Agent 负责：

- 理解作者意图和作品上下文；
- 构思、规划、推演、写作和修改；
- 审校、考据、状态提取和问题诊断；
- 根据角色输出结构化结果或直接修改授权范围内的文件；
- 解释建议依据，并接受作者反馈。

### 4.3 Git

**[已确认]** Git 负责：

- 作品重要文件的版本记录；
- 展示人类和 Agent 的文件差异；
- 提供恢复、分支和跨电脑迁移的基础能力；
- 在作者明确授权后形成提交。

**[已确认]** Git 不负责承载实时 Agent 通信，仓库文件不作为 Agent 之间的消息队列。

## 5. Agent 角色体系

角色可以由不同 Agent 会话承担，也可以由同一种 Agent 的多个会话承担。角色不是强制全部常驻。

| 角色 | 主要职责 | 默认是否改正文 |
|---|---|---|
| Writer | 续写、重写、扩写、压缩、润色和按任务修改正文 | 是，在任务授权范围内 |
| Observer | 持续观察、划词评论、收集反馈、复查修改 | 否 |
| 创作导航器 | 判断当前阶段，维护主线任务，组织下一步和剧情路线 | 否，负责协调 |
| Story Architect | 全书、分卷、章节、场景结构与剧情推演 | 否，除非另行授权 |
| Canon Keeper | 人物状态、时间线、知识边界、伏笔和设定一致性 | 否，生成候选变更 |
| Style Coach | 风格一致性、写作基本功分析和针对性训练 | 默认否 |
| Researcher | 拆解资料问题、检索、整理来源和事实卡 | 否 |
| Editor | 结构、节奏、因果、语言和可读性审校 | 默认否 |
| Release Assistant | 标题、简介、标签、发布检查和读者反馈整理 | 否，不得自动发布 |
| 记忆整理员 | 从长期反馈中提炼作者偏好、作品风格和能力候选规则 | 否 |

**[已确认]** 同一时刻只能有一个“当前主线任务”。其他角色可以提出建议任务，但不能绕过创作导航器同时向作者推送多个互相冲突的主线。

## 6. 核心用户旅程

### 6.1 从零开始一本小说

**目标：** 作者可以从一句灵感、一个人物、一个世界观或完全空白开始，快速进入可写状态。

**[已确认]** 系统必须像游戏指引一样告诉作者当前阶段、为什么要做这一步、下一步做什么，并根据作品变化动态调整。

**[已确认]** 流程：

1. 作者选择新建系列/作品，输入已有灵感；也可以选择“我什么都没有”。
2. Agent 先分析已有信息并生成候选方向，不让作者填写大量术语化表单。
3. 系统只询问会显著改变作品方向的少量问题。
4. 生成“最小可开书包”：故事承诺、主角当前欲望、核心冲突、失败代价、开篇事件和第一章场景目标。
5. 作者确认、组合、修改或拒绝候选方向。
6. 系统创建当前主线任务和最多三个下一步。
7. 作者自己写第一章，或交给 Writer。
8. Observer 对写作结果给出评论，创作导航器据此更新下一步。

**完成结果：** 作者无需先完成完整世界观或全书大纲，也能开始第一章；确认过的决定进入作品资料，未确认内容保持为建议。

### 6.2 作者直接写作，Observer 陪跑

1. 作者打开仓库，系统显示上次停留位置、当前目标、下一步和阻塞项。
2. 作者主动开启 Observer 会话。
3. 作者在编辑器中继续写作，内容可以尚未保存。
4. Observer 在合适的停顿或手动触发后分析不可变文本快照。
5. 建议以划词评论、对象评论或会话汇总展示。
6. 作者接受、拒绝、修改、暂缓或要求解释。
7. 正文变化后，Observer 复查原问题是否解决。
8. 关闭 Observer 会话后停止持续观察。

### 6.3 Writer Agent 写作，Observer Agent 审查

1. 作者或创作导航器创建写作任务，明确范围、目标和完成条件。
2. Writer 直接修改正文文件。
3. 工作台检测文件变化并保留可查看的 Git diff。
4. Observer 对 Writer 的结果进行独立审查。
5. 普通问题形成评论；阻塞问题通过平台消息通道反馈给 Writer。
6. Writer 修改后，Observer 复查。
7. 作者可以随时暂停 Agent、接管编辑或拒绝建议。
8. 只有作者明确要求时，才允许形成 Git 提交。

### 6.4 作者卡文

1. 作者点击“我卡住了”或直接向 Agent 描述问题。
2. 系统自动准备当前场景目标、角色动机、冲突、伏笔、风格和近期正文。
3. Agent 先诊断卡文类型，例如目标不清、阻力不足、因果断裂、情绪未到位、信息过早耗尽或作者尚未做关键决定。
4. Agent 给出多个解决路线，并说明每条路线的效果、代价和对后续剧情的影响。
5. 作者选择、组合、要求重新推演，或让 Writer 直接执行。
6. 选中的路线成为当前任务或计划候选；未选择路线不进入正式正典。

### 6.5 换电脑继续写

1. 作者在另一台电脑安装工作台和至少一个受支持 Agent。
2. 克隆或复制系列 Git 仓库。
3. 工作台识别仓库和数据版本，重建可重建索引。
4. 系统恢复正文、已确认设定、目标、任务、重要评论和作品级风格。
5. 作者级全局风格从独立作者档案恢复或重新关联。
6. Agent 登录凭据由各 Agent 自己管理，不写入仓库。

## 7. 智能创作导航

### 7.1 导航目标

**[已确认]** 创作导航需要覆盖从开书到持续创作，而不是只在第一次使用时显示固定教程。

它持续回答：

- 作品现在处于什么阶段；
- 当前最重要的创作目标是什么；
- 为什么此刻应该处理它；
- 作者或 Agent 下一步具体做什么；
- 完成后怎样判断有效；
- 如果偏离原计划，应该更新计划还是调整正文。

### 7.2 创作旅程

**[已确认]** 基础阶段包括：

1. 灵感与创作意图；
2. 题材、读者期待和故事承诺；
3. 主角、核心冲突和长期故事发动机；
4. 最小可开书设定；
5. 开篇和前三章；
6. 当前卷和近期剧情；
7. 逐章创作、观察和修订；
8. 分卷收束和下一卷启动；
9. 完结、全书修订和发布准备。

阶段不是强制瀑布流程。系统应允许跳过、回退、补做或并行处理。

### 7.3 任务卡

**[已确认]** 每张引导任务卡至少包含：

- 任务名称；
- 所属层级：系列 / 作品 / 卷 / 章 / 场景 / 会话；
- 为什么现在要做；
- 已知信息；
- 仍缺少的关键决定；
- AI 已经完成的预分析；
- 作者必须决定的事项；
- Agent 可以代做的工作；
- 完成条件；
- 关联正文、设定、评论和后续影响；
- 来源和可信状态。

任务入口包括：“让 AI 直接完成”“先给方案”“我自己处理”“暂缓”“跳过”“不适合我的写法”。

### 7.4 规划方式

**[已确认]** 支持随时切换：

- 大纲模式：先规划全书和分卷；
- 滚动规划：保留全书方向，详细规划当前卷和未来数章；
- 探索模式：只确定当前场景和未来一至三章；
- 托管模式：作者只批准高影响决定，其余由 Agent 执行。

### 7.5 引导强度

**[已确认]**

- 教学：解释术语、方法和为什么这样做；
- 陪跑：只显示当前任务、下一步和必要提醒；
- 自由：仅在卡文、严重冲突或作者主动询问时出现。

### 7.6 动态剧情引导

**[已确认]** 系统根据以下状态推演下一步：

- 角色当前欲望、情绪、关系和知识；
- 当前冲突与失败代价；
- 读者已经知道和期待知道的内容；
- 未兑现的伏笔、悬念和承诺；
- 当前章节功能、节奏与张力；
- 已确认的卷目标和结局方向；
- 作者风格、内容边界和最近反馈。

每条剧情路线应说明预期效果、因果链、代价、风险、影响的后续计划和需要新增的铺垫。系统不得把单一套路包装成唯一正确答案。

### 7.7 偏航处理

**[已确认]** 当正文偏离计划时，系统应先询问这是否为作者有意产生的新方向，并提供：

- 更新计划以接受新方向；
- 调整当前正文以回到原计划；
- 暂时保留分支，继续观察；
- 启动剧情推演比较两条路线。

未经作者确认，创作导航器不能把推断的新方向写成已确认正典。

## 8. 编辑、保存与恢复快照

### 8.1 编辑器

**[已确认]**

- 支持 Markdown 和 TXT；
- Agent 可以直接修改正文文件；
- 不设独立 AI 草稿层；
- 作者通过当前正文和 Git diff 审查修改。

**[已确认]** 编辑器提供章节树、搜索、字数、焦点模式、Markdown 基础格式和正文/预览切换，但不追求通用 IDE 能力。

### 8.2 保存模式

**[已确认]** 支持：

- 保存按钮和 `Ctrl/Cmd + S`；
- 停止输入 N 秒后的智能自动保存，可关闭并配置时间；
- 切换章节、窗口或应用时保存，可单独开关。

智能自动保存基于停止输入，而不是固定间隔强制保存。

### 8.3 四条独立状态链

**[已确认]** 以下概念必须严格分开：

1. 保存：缓冲区写入磁盘文件；
2. Git 提交：形成版本节点；
3. Observer 分析：读取一个文本快照；
4. 恢复快照：崩溃恢复，不代表正式保存。

自动保存不得触发 Git 提交。关闭自动保存时，系统仍可在仓库外保留崩溃恢复快照。

### 8.4 编辑器状态

**[已确认]** 状态栏至少区分：

`未保存`、`正在保存`、`已保存`、`Agent 正在修改`、`Observer 分析中`、`分析结果已过期`、`存在冲突`。

### 8.5 已确定默认值

- **[已确认]** 智能自动保存默认开启，默认在停止输入 5 秒后保存；作者可以修改等待时间或关闭。
- **[已确认]** 失焦保存默认开启。切换文件、章节、项目窗口或应用时，如果缓冲区有修改则保存；作者可以关闭。
- **[已确认]** 恢复快照采用以下默认策略：
  - 缓冲区有未保存变化时，最多每 30 秒生成一次恢复点；相同内容不重复保存；
  - 在 Agent 修改交付、外部文件重载、冲突合并和应用退出等可能影响缓冲区的动作前额外生成恢复点；
  - 普通恢复点保留 30 天；
  - 单个小说仓库最多占用 500 MB，全部项目合计最多占用 2 GB；
  - 达到时间或空间上限时优先清理最旧的恢复点，但始终保留每个仍在编辑文件的最新恢复点和上一次写作会话结束点；
  - 恢复快照使用增量或去重存储，位于仓库外，不进入 Git diff，也不随 Git 提交。

30 天用于覆盖误删后隔一段时间才发现的情况；500 MB 对纯文本小说足以保留大量增量版本，同时不会让单个项目无限占用磁盘。

## 9. Observer

### 9.1 生命周期

**[已确认]**

- 作者主动开启 Observer 会话；
- 会话开启期间持续跟踪人类或 Agent 的写作；
- 关闭会话后停止观察；
- 作者决定是否采纳建议。

### 9.2 不可变分析快照

**[已确认]** Observer 分析工作台生成的不可变文本快照，而不是只读取磁盘文件，因此可以分析未保存的编辑器内容。

每次请求至少关联：快照 ID、文本哈希、编辑器版本、分析范围和周边上下文。

结果返回时：

1. 目标文字未变：正常显示评论；
2. 其他文字变化但目标未变：根据差异重新定位；
3. 目标本身变化：标记“基于旧版本”，不挂到新文字上；
4. 目标删除或重写：标记过期，可请求重新分析。

硬规则：不能把 Observer 针对旧文字的意见冒充为针对当前文字的有效意见。

### 9.3 触发策略

**[已确认]** 自动保存与 Observer 分析解耦。可用触发方式：

- 作者停止输入一段时间且累计修改达到阈值；
- 完成场景或章节；
- Writer 完成任务；
- 作者点击“立即检查”；
- 作者选中文字定向询问。

Observer 应合并短时间内的连续变化，只处理最新待分析版本，减少过期结果和配额浪费。

### 9.4 评论形式

**[已确认]** Observer 建议通过直观的划词评论展示，并提供反馈入口。

**[已确认]** 评论可以锚定：

- 一段正文；
- 章节或场景；
- 人物、设定、时间线或伏笔；
- 整个写作会话。

评论至少包含：问题类型、严重程度、简明结论、依据、建议动作、来源快照和关联任务。

### 9.5 作者反馈

**[已确认]** 作者可以：

- 接受；
- 拒绝并说明理由；
- 修改后请求复查；
- 暂缓；
- 要求解释。

反馈既影响当前评论，也可成为 Observer 和写作角色改进的证据。

### 9.6 修改后复查

**[已确认]** 评论形成闭环：提出问题 → 作者反馈/正文修改 → Observer 对比修改前后 → 给出复查结果。

复查结果：

- 已解决；
- 部分解决；
- 尚未解决；
- 引入新问题；
- 作者有意保留，不再追踪；
- 原建议因剧情变化失效。

已解决问题在原线程中关闭；部分解决或尚未解决的问题重新锚定；新问题创建关联评论。默认每次修改只自动复查一次，避免无限循环。

### 9.7 通知原则

**[已确认]**

- 普通建议进入侧栏和阶段汇总，不弹窗打断；
- 严重连续性冲突、数据丢失风险和 Agent 覆盖风险可以即时提醒；
- 作者可以调节低频、标准、高频模式；
- 评论过多时按场景或章节聚合。

## 10. 目标、任务与项目打开页

### 10.1 继续创作卡

**[已确认]** 打开项目默认先显示：

- 系列 / 作品 / 卷 / 章 / 场景位置；
- 当前创作阶段；
- 上次停留位置；
- 当前章目标和本次创作焦点；
- 最多三个下一步；
- 真正阻塞写作的问题；
- 未处理的重要评论。

主要动作：继续写作、交给 Writer、启动 Observer、处理阻塞、查看完整计划。

### 10.2 目标层级

**[已确认]**

`系列目标 → 作品目标 → 卷目标 → 章节目标 → 当前写作目标`

目标权威顺序：

1. 作者固定的目标；
2. 当前明确执行的任务；
3. 从已确认计划推导的目标；
4. Agent 自动生成的建议目标。

Agent 可以更新进度、补充待办、发现阻塞，但不能悄悄替换作者固定目标。

### 10.3 任务结构

**[已确认]** 任务应具备：

- 状态：现在 / 下一步 / 阻塞 / 已完成；
- 类型：写作 / 设定 / 考据 / 修订 / 审校 / 发布；
- 执行者：作者或某个 Agent 角色；
- 来源：作者、计划、Observer 或 Agent 建议；
- 关联对象：文件、章节、人物、设定、评论；
- 完成条件。

**[已确认]** 增加任务范围、优先级、创建时间、依赖、执行记录和取消原因。

## 11. 长篇上下文与故事记忆

### 11.1 上下文组装器

**[已确认]** 长篇小说不能依赖把整个仓库无差别交给 Agent。每个任务由系统准备可检查的上下文包，至少包括：

- 当前任务和完成条件；
- 当前正文范围及相邻章节；
- 当前章、卷和作品目标；
- 相关人物状态、关系和知识；
- 相关世界规则与时间线；
- 未兑现的伏笔、悬念和叙事承诺；
- 当前 POV、叙事声音和作者风格要求；
- 最近确认的决定与相关评论；
- 来源位置和上下文取舍原因。

作者可以查看“本次 Agent 看到了什么”，补充或排除内容。Agent 的结论应能区分“上下文不足”和“基于充分上下文的判断”。

### 11.2 故事事实状态

**[已确认]** 所有结构化故事信息标记为：

- 作者已确认；
- 正文明确出现；
- Agent 推断；
- AI 建议；
- 存在冲突；
- 已废弃但保留历史。

Agent 不得把推断或建议自动升级为已确认事实。

### 11.3 设定变更与追溯

**[已确认]** 人物、世界规则、时间线、知识边界和伏笔条目应关联正文证据。修改已确认正典时，系统生成影响分析：

- 与哪些章节冲突；
- 哪些计划需要调整；
- 哪些人物状态和伏笔受影响；
- 是否属于有意追溯修改；
- 是否需要创建新的修订任务。

### 11.4 风格和写作能力记忆

**[已确认]** 系统需要提炼并保存作者、作品、角色声音和写作基本功，使风格保持一致并持续提升。

**[已确认]** 记忆作用域：

- 作者级：跨系列的长期偏好与能力；
- 系列级：共同世界的语调、边界和叙事规范；
- 作品/POV 级：具体叙事距离、角色声音和用词；
- 会话级：本次任务的临时例外，不自动沉淀。

Observer 只收集反馈和证据。记忆整理员在多次重复证据后提出候选规则，由作者确认后才进入长期风格。单次拒绝不能自动改写作者画像。

## 12. Agent 桥接与协作协议

### 12.1 Agent Hub

**[已确认]** 工作台桥接完整的通用 Agent，而不是直接连接模型 API。

**[已确认]** Agent Hub 负责：

- 启动、连接、暂停、恢复和终止 Agent 会话；
- 注入角色、任务和上下文包；
- 把 Agent 输出转为工作台事件；
- 转发 Agent 间消息；
- 记录任务状态、能力、错误和文件变化；
- 暴露统一操作，但保留不同 Agent 的能力差异。

### 12.2 适配器能力声明

**[已确认]** 每个 Agent 适配器明确声明是否支持：

- 持续会话；
- 会话恢复；
- 中途追加消息；
- 取消任务；
- 结构化输出；
- 文件修改；
- Agent 间通信；
- 工具审批事件；
- 用量/成本返回。

工作台不得把不支持的能力伪装成可用；降级行为必须可见。

### 12.3 平台消息通道

**[已确认]** 工作台是 Agent 之间的消息总线，至少支持语义操作：

- 发送消息；
- 创建/回复评论；
- 提问和请求作者决定；
- 分派任务；
- 移交任务；
- 更新状态；
- 提交反馈。

仓库文件不作为实时 Agent 邮箱。

### 12.4 任务生命周期

**[已确认]**

`待执行 → 运行中 → 等待作者 → 等待复查 → 已完成`

任意运行状态还可以进入：`已取消`、`已中断`、`失败`、`已过期`。

Agent 断开或应用重启后，不得默默重复执行已产生文件改动的步骤。恢复前先检查任务记录和当前文件哈希。

## 13. 并发编辑与冲突

### 13.1 基本原则

**[已确认]** 工作台必须同时跟踪：

- Agent 开始任务时的基础文件；
- 作者当前未保存缓冲区；
- 磁盘上的最新文件；
- Agent 完成后的文件。

Agent 不得用磁盘文件覆盖作者尚未保存的缓冲区。

### 13.2 三方合并

当作者和 Agent 修改同一文件时：

- 修改范围不重叠：自动合并并提示；
- 修改范围重叠但可以可靠重定位：展示建议合并结果；
- 同一段发生实质冲突：进入三方比较，由作者选择或编辑；
- 作者可以整批接受、逐段接受、保留自己版本或取消 Agent 修改。

### 13.3 外部编辑器变化

**[已确认]** 工作台监控仓库文件变化。检测到外部编辑器或其他进程修改时：

- 当前缓冲区无未保存修改：重新加载并保留光标；
- 当前缓冲区有未保存修改：禁止静默重载，进入比较；
- Observer 正在分析：按照快照版本规则处理结果；
- Agent 正在修改同一文件：暂停交付并进行冲突检查。

## 14. 权限与作者控制

### 14.1 权限原则

- **[已确认]** 修改正文不等于获得 Git 提交权限。
- **[已确认]** 作者可以手动提交，也可以明确要求 Agent 提交。
- **[已确认]** 未明确授权时，Agent 修改后不得自动提交。
- **[已确认]** Agent 可以自动维护作品状态和待办。
- **[已确认]** 高风险权限按动作授权，不以一句“你来写吧”无限扩张。

### 14.2 默认权限矩阵

| 动作 | 默认策略 |
|---|---|
| 读取当前仓库 | 当前会话允许 |
| Observer 创建评论 | Observer 会话开启后允许 |
| Writer 修改任务指定正文 | 分派写作任务后允许 |
| 更新进度、任务和可重建索引 | 允许并展示变更 |
| 新建普通规划/资料文件 | 任务范围内允许并展示变更 |
| 修改已确认正典 | 只生成候选，作者确认后应用 |
| 修改长期作者风格 | 只生成候选，作者确认后应用 |
| 删除、移动、大规模重命名文件 | 每次明确确认 |
| 大规模重写超出任务范围的正文 | 请求扩大任务范围 |
| Git status / diff / log | 允许 |
| Git stage / unstage | 仅在作者明确命令后执行；明确要求提交时，同时授权暂存该次提交范围内的文件 |
| Git commit | 必须明确授权 |
| Git push / pull / merge / rebase | 分别明确授权 |
| 强制推送、丢弃改动、破坏性重置 | 高风险二次确认 |
| 联网检索 | 按任务/会话授权；Researcher 可在任务开始时一次申请本任务所需范围，不形成永久授权 |
| 向新的第三方上传未公开正文 | 每次明确确认 |
| 对外发布、发消息或创建公开内容 | 每次明确确认 |

### 14.3 紧急控制

**[已确认]** 工作台提供：暂停当前 Agent、停止全部 Agent、取消排队任务、撤销本次可逆修改、查看仍在运行的外部进程。

## 15. Git 与版本管理

### 15.1 仓库边界

**[已确认]** 一个故事世界/系列一个 Git 仓库。仓库可包含共享设定和多本作品；独立小说使用相同结构但只有一本作品。

### 15.2 工作区状态

**[已确认]** 打开仓库时显示：

- 当前分支；
- 未提交文件数；
- 哪些变化来自作者、Agent 或无法判定的外部进程；
- 是否存在冲突；
- 最近提交和距离上次检查点的变化。

若仓库打开时已经有未提交改动，工作台必须保留并标记为“打开前已有”，不能把它们归因于当前 Agent。

### 15.3 提交

**[已确认]** 提交只在作者明确授权后发生。

**[已确认]** Agent 可以准备提交说明和建议包含的文件，但在授权前不执行 stage 或 commit。完成卷、重大设定变更或发布版本时，系统可以建议创建检查点，但不得自动执行。

### 15.4 远端操作

**[已确认]** Git remote 是可选能力。工作台不默认推送，不把远端 Git 等同于公开发布，也不假设远端仓库一定私有。

## 16. 数据、迁移与隐私

### 16.1 三类数据

**[已确认]**

1. **Git 权威数据**：正文、已确认正典、计划、目标、重要任务、确认过的风格规则和决策记录。
2. **项目结构化状态**：开放评论、评论线程、Agent 任务记录、位置锚点、会话摘要和运行状态。重要部分必须随仓库迁移或提供可靠导出。
3. **可重建缓存**：全文索引、向量索引、统计和 UI 缓存，删除后可从前两类数据重建。

### 16.2 数据落盘原则

- 任何不可重建且会影响继续创作的信息，不能只存在某台电脑的应用数据库中；
- 高频、低价值 UI 状态不应持续污染 Git diff；
- 项目元数据需要版本号和显式迁移机制；
- 凭据、Token、API Key、登录状态和本机绝对路径不得提交到作品仓库；
- 所有自动提取内容保留来源和确认状态。

### 16.3 作者档案

**[已确认]** 跨作品的作者风格、长期偏好和写作能力不绑定单一小说仓库，使用独立、可导出、可导入的作者档案。作品仓库只保存对该作品生效的引用或快照。

### 16.4 为什么不能只选一种存储

**[已确认]** 不建议把全部数据都放在同一种介质中：

- 全部写成仓库文本：最便于迁移和查看，但搜索、评论定位和高频运行状态会产生大量 Git 噪声；
- 全部放在本机数据库：运行最快，但换电脑后会丢失评论、任务和创作过程；
- 把一个 SQLite 数据库直接提交到 Git：文件是二进制，几乎无法审查 diff，也很容易产生合并冲突；
- 只保存最终正文：无法恢复 Agent 为什么修改、作者为什么拒绝建议以及当前任务做到哪里。

因此推荐“仓库中的持久记录 + 本机数据库索引 + 仓库外恢复快照”的混合方案。

### 16.5 推荐混合数据方案

**[已确认]**

#### A. 随 Git 仓库迁移的内容

这些内容决定“作品是什么”以及“接下来怎么继续”，必须跨电脑保留：

```text
series-repo/
├── manuscript/                  # Markdown/TXT 正文
├── canon/                       # 已确认人物、世界、时间线、知识边界
├── planning/                    # 系列、作品、卷、章与场景计划
├── decisions/                   # 作者确认过的高影响决定
└── .novel/
    ├── manifest.json            # 项目标识、数据版本、书目结构
    └── events/
        └── 2026-08/
            ├── session-xxx.jsonl
            └── session-yyy.jsonl
```

- 正文、正典、规划和重要决定优先使用 Markdown/TXT，并在需要结构化字段时使用少量 YAML front matter 或 JSON；
- `.novel/events/` 保存平台必须记住的结构化事件：目标和任务变化、评论与回复、作者反馈、评论解决状态、Agent 任务摘要、文件变更摘要和确认记录；
- `JSONL` 表示“一行一个事件”。新增记录通常只会在 Git diff 中多一行，不需要反复重写一个大型数据库；
- 事件按月份和写作会话分段，避免单个文件无限变大，也减少不同会话写入同一文件的冲突；
- 历史事件只追加。纠正旧信息时写入新的更正事件，不悄悄改写历史；
- 工作台负责把这些文件渲染成评论、任务卡和时间线，作者正常情况下不需要手工阅读 JSONL。

概念示例：

```jsonl
{"type":"comment.created","id":"OBS-17","target":"chapter-12","snapshot":"S42"}
{"type":"comment.feedback","id":"OBS-17","decision":"modified","reason":"保留人物的情绪失控"}
{"type":"comment.resolved","id":"OBS-17","result":"resolved"}
```

实际记录还会包含时间、来源 Agent、锚定文字、文件哈希和数据版本；示例只用于说明事件是怎样连续追加的。

#### B. 只放本机、可以重建的工作数据库

工作台在系统应用数据目录中维护一个本地数据库，用于：

- 快速搜索全文、人物、评论和任务；
- 保存当前评论锚点的计算结果；
- 维护 Agent 任务队列、进度条和临时输出；
- 保存界面布局、光标、折叠状态和最近打开记录；
- 缓存向量索引、统计结果和上下文候选；
- 暂存完整 Agent 终端输出和调试日志。

这个数据库不提交 Git，也不是事实源。删除或换电脑后，工作台应能从正文、正典、规划和 `.novel/events/` 重建重要状态。无法重建的内容不得只放这里。

#### C. 仓库外的恢复快照

未保存缓冲区和临时恢复版本按第 8.5 节保存在仓库外。它们用于同一台电脑上的崩溃恢复，不作为作品历史，也不跟随普通 Git 克隆。

#### D. 独立作者档案

跨作品的作者风格、长期偏好和能力记录使用单独的作者档案包。它不默认复制进每个小说仓库，但可以导出、导入或存放在作者自行管理的私有 Git 仓库中。

### 16.6 哪些记录跨电脑保留

| 数据 | 随仓库迁移 | 说明 |
|---|---|---|
| 正文、正典、规划、已确认决定 | 是 | 作品核心事实 |
| 当前目标、任务及完成历史 | 是 | 否则换电脑后不知道做到哪里 |
| Observer 评论、线程、作者反馈、复查结果 | 是 | 同时用于长期风格学习 |
| Agent 任务目标、结果、状态和文件变更摘要 | 是 | 用于审计、恢复和任务移交 |
| Agent 完整终端输出、逐 Token 流和调试日志 | 默认否 | 体积大、价值低；需要时可单独导出 |
| 当前像素位置、临时评论坐标 | 否 | 根据文本锚点重新计算 |
| 全文/向量索引和统计缓存 | 否 | 可以重建 |
| 未保存正文恢复点 | 默认否 | 同机崩溃恢复；跨电脑前应保存或导出 |
| API Key、登录状态和本机路径 | 永不 | 新电脑重新登录或配置 |

### 16.7 Git 噪声与迁移体验

**[已确认]**

- 工作台的变更面板分为“正文与设定”和“系统记录”，系统记录默认折叠但绝不隐藏；
- Agent 自动维护任务、评论和状态时可以直接写入 `.novel/events/`，但不会因此自动 stage 或 commit；
- 作者准备提交时，工作台建议把与本次正文相关的系统记录一起纳入提交，并生成易读摘要；
- 使用远端 Git 换电脑时，只有已经明确提交并推送的内容能通过克隆恢复；工作台应在迁移前提示尚未提交的正文和系统记录；
- 不希望提交时，作者可以通过“迁移包”或完整复制仓库工作目录带走尚未提交内容；
- 新电脑打开仓库后，工作台读取 `.novel/manifest.json`，重放事件并重建本地数据库。

### 16.8 本方案需要作者评估的产品取舍

作者无需评估数据库或文件格式本身，只需判断以下体验是否符合预期：

1. 重要评论、任务、反馈和 Agent 结果摘要会成为仓库的一部分，可以随 Git 迁移；
2. Git 变更中会出现少量 `.novel/events/` 系统记录，但工作台会与正文分组展示；
3. 完整 Agent 原始日志默认只留本机，跨电脑只保留足以继续任务的摘要；
4. 未提交的内容不会凭空出现在另一台电脑，系统会引导作者显式提交/推送或生成迁移包；
5. 本机数据库损坏不会破坏作品，最多丢失可重建缓存和不重要的界面状态。

## 18. 成本、频率与隐私控制

### 18.1 Observer 消耗控制

**[已确认]**

- 支持低频、标准、高频和手动模式；
- 设定每次会话或每日分析预算；
- 显示排队任务、当前 Agent 和可获得的用量信息；
- 连续输入期间不重复创建分析任务；
- 新版本到达时，尚未开始的旧分析可以被最新任务取代；
- 已返回但过期的结果不作为当前评论展示。

### 18.2 隐私

**[已确认]**

- 工作台使用已安装 Agent 自己的认证，不保存模型 API Key；
- 明确提示正在使用哪个 Agent，以及哪些正文将进入其上下文；
- 切换到新的第三方 Agent 时重新提示数据边界；
- 未经授权不把未公开全文发送到额外的搜索、分析或发布服务；
- 日志默认不记录凭据，也不无期限复制完整正文。

## 19. 异常与恢复

| 场景 | 预期行为 |
|---|---|
| 工作台崩溃 | 恢复未保存缓冲区，明确区分恢复内容与磁盘文件 |
| Agent 崩溃/断连 | 任务进入中断状态；保留已产生 diff；不得默默重复执行 |
| Observer 结果迟到 | 按快照校验；过期结果不挂到当前文字 |
| 作者与 Agent 同改一段 | 进入三方比较，不覆盖作者缓冲区 |
| 外部程序修改文件 | 检测变化；有未保存内容时禁止静默重载 |
| 元数据损坏 | 从 Git 权威数据重建可重建部分；不可重建数据给出明确恢复提示 |
| 应用升级 | 识别数据版本，先备份再执行显式迁移 |
| 换电脑 | 克隆仓库后恢复项目，重建缓存，重新连接 Agent 和作者档案 |
| Git 存在未提交改动 | 保留并标记打开前状态，不归因于当前 Agent |
| 权限请求无人处理 | Agent 暂停等待，不自行扩大权限或改用高风险替代方案 |

**[已确认]** 所有可变更正文的 Agent 任务都应具备任务 ID、开始时文件哈希、结束状态和实际变更列表，以支持恢复与审计。

## 20. MVP 功能范围

### 20.1 必须包含

1. 打开并识别一个系列 Git 仓库；
2. 舒适编辑 Markdown/TXT，支持手动和可配置自动保存；
3. 崩溃恢复快照；
4. 系列、作品、卷、章的基本结构化导航；
5. 继续创作卡、当前目标、下一步和任务；
6. 从一句灵感引导到可以开始第一章；
7. 基于当前故事状态生成下一步剧情路线；
8. 一个主要 Agent 适配器，可以作为 Writer 直接修改正文；
9. 第二个独立会话可以作为 Observer；
10. Observer 的快照分析、划词评论、反馈和复查闭环；
11. Agent 修改与作者未保存内容的冲突保护；
12. Git status、diff 和显式提交入口；
13. 最小故事记忆：人物状态、时间线、知识边界、伏笔和来源；
14. 任务相关上下文包及“Agent 看到了什么”；
15. 仓库换电脑后可恢复关键项目状态；
16. 停止 Agent、失败可见、任务不重复执行。

### 20.2 用第二个 Agent 验证但不追求能力完全一致

**[已确认]** MVP 至少用第二个 Agent 验证：

- 适配协议不是只为一个产品硬编码；
- 能力声明和降级机制有效；
- Writer 与 Observer 可以由不同通用 Agent 承担。

### 20.3 工具层通用性硬门

**[已确认]** 产品核心不得为当前验收小说或某一种题材硬编码。作品名、人物名、世界观、卷章、题材规则、当前仓库路径和专属工作流必须保存在作品 Git 仓库、可替换配置、模板或验收夹具中。

- `src/`、`electron/`、通用数据模型、Agent 桥接、Observer、任务/目标/事实/评论、恢复与 Git 能力只依赖抽象协议；
- 项目专用脚本可以用于真实长篇验收，但不是启动或使用平台的前置；
- 删除任一验收作品后，工作台仍须能打开新的 Markdown/TXT 小说仓库并完成全部通用闭环；
- 发布前运行 `npm run audit:generic`，核心代码出现验收项目标识、固定 `workspaces/<project>` 路径或对 `scripts/` 的运行依赖即失败；
- 至少用另一题材、另一目录结构和 TXT 正文做一次新项目验收，防止“数据可配置、流程仍写死”。

### 20.4 MVP 不包含

**[MVP 外]**

- 多人实时协作；
- 移动端完整编辑；
- Word、在线文档和富文本编辑；
- 云端账户体系和官方云同步；
- 一键连接所有 Agent；
- 自动发布和平台运营数据回流；
- 读者评论大规模聚类；
- 封面生成、音频、漫画、短剧等 IP 延展；
- 完整资料库与专业领域事实门禁；
- 插件市场；
- 复杂游戏化积分和成就系统。

## 21. MVP 验收标准

### 21.1 五条闭环旅程

#### A. 从灵感到第一章

- 作者只输入一句灵感也能开始；
- AI 先给候选方案，不要求填写大量表单；
- 作者确认关键方向后，系统生成当前任务和第一章目标；
- 作者或 Writer 可以开始正文；
- 未确认建议不进入正式正典。

#### B. 作者写作 + Observer

- Observer 能分析未保存缓冲区的快照；
- 评论准确锚定原文；
- 正文变化后，旧评论能够重定位、过期或重新分析；
- 作者反馈进入评论线程；
- 修改后可完成一次复查闭环。

#### C. Writer + Observer

- Writer 在授权范围内直接修改正文；
- 全部修改可在 Git diff 中查看；
- Observer 独立审查并把阻塞问题反馈给 Writer；
- 作者可暂停、接管或拒绝；
- 未经明确授权不会产生 Git 提交。

#### D. 卡文处理

- 系统自动准备相关上下文；
- Agent 先诊断问题，再给多条路线；
- 每条路线说明效果、代价和后续影响；
- 作者可以选择、组合、拒绝或交给 Writer；
- 只有确认路线才更新任务或计划。

#### E. 跨电脑恢复

- 克隆仓库后正文、正典、目标、任务和重要评论可恢复；
- 缓存可重建；
- 凭据无需也不得从仓库恢复；
- 数据版本不兼容时给出迁移流程，不静默破坏数据。

### 21.2 硬性不变量

MVP 必须满足：

1. 旧版本 Observer 意见绝不冒充当前版本意见；
2. Agent 绝不覆盖作者未保存缓冲区；
3. 未经授权绝不执行 Git commit；
4. Agent 中断后绝不默默重复已产生副作用的步骤；
5. AI 推断绝不自动升级为作者确认的正典；
6. 所有 Agent 正文修改都能通过 diff 查看；
7. 重要创作状态不能只存在单台电脑的临时数据库；
8. 作者可以随时停止 Agent 并继续手工写作；
9. 打开项目后能快速知道写到哪里和下一步做什么；
10. 工作台本身不保存通用 Agent 的模型凭据。

### 21.3 技术原型优先验证

正式开发 MVP 前，技术原型优先验证：

1. 通用 Agent CLI 的启动、会话、取消、权限与事件桥接；
2. 作者缓冲区、磁盘文件和 Agent 修改的三方合并；
3. Observer 评论在持续编辑后的重新定位；
4. 长篇上下文包的选择、来源展示和预算控制；
5. 关键项目数据在换电脑后的重建与恢复。

原型只证明关键风险可行，不等于实现完整产品。

## 22. 非功能需求

### 22.1 数据安全

- 默认本地运行；
- 写入采用可恢复策略；
- 高风险动作显式确认；
- 任何破坏性操作先解析精确目标；
- 不在日志、仓库和迁移数据中保存凭据。

### 22.2 可解释性

- Agent 建议显示来源、作用范围和可信状态；
- 上下文包可查看；
- 自动维护的目标、任务和正典变化可追踪；
- 失败和降级不可隐藏。

### 22.3 可移植性

- 作品重要数据采用开放或有公开迁移定义的格式；
- 项目元数据带版本；
- 缓存可重建；
- 不把业务事实绑定到某个 Agent 厂商。

### 22.4 可用性

- 默认界面以正文为中心；
- 不要求作者理解 Agent 协议或 Git 命令；
- 不用大量弹窗打断连续写作；
- 高级结构化信息按需展开；
- 作者始终能看见当前保存、Agent、Observer 和 Git 状态。

### 22.5 可测试性

**[已确认]** 建立小型示例小说仓库和固定场景，用于重复测试：评论重定位、设定冲突、人物知识边界、并发修改、Agent 中断、权限门禁和跨电脑恢复。由于 Agent 输出有随机性，验收以行为约束和闭环完成为主，不以唯一文本答案为准。

## 24. 已确认的 MVP 默认决策

作者已确认采用 V0.1 中的全部推荐默认方案。以下内容不再阻塞后续产品设计；作者仍可通过新的明确决定修改默认值。

### 24.1 MVP 目标用户

第一版聚焦单人中文长篇网文作者、本地桌面工作台、Git 系列仓库和 Markdown/TXT 正文。用户已安装并登录至少一个受支持的通用 Agent。多人协作、移动端和富文本不进入 MVP。

### 24.2 首批 Agent

- 第一个完整适配：Codex CLI；
- 第二个协议验证适配：Claude Code；
- 统一适配协议不得写死为只支持这两个 Agent；
- Copilot、TraeX 和其他 Agent 在协议稳定后按能力声明接入。

选择顺序只决定原型和 MVP 的实现优先级，不代表作品数据依赖 Codex 或 Claude。

### 24.3 首发操作系统

- 首个正式支持的桌面系统：macOS；
- 数据格式、仓库规范、Agent 协议和核心领域逻辑必须跨平台；
- Windows 是下一优先级；Linux 在核心协议中保持兼容，但不阻塞首个 MVP；
- “换电脑继续写”的作品数据保证不依赖 macOS 专有格式。

### 24.4 Observer 标准模式

Observer 默认使用标准频率：

- 作者停止输入 20 秒，并且自上次分析后累计新增或修改不少于 150 个中文字符，或已经完成一个自然段时，可以触发自动分析；
- 两次普通自动分析至少间隔 90 秒；
- 场景/章节完成、Writer 任务完成和作者手动检查可以立即触发，不受普通间隔限制；
- 同一范围存在多个等待任务时，只保留最新文本版本的分析任务；
- 每个 Observer 会话默认提供 40 次普通自动分析的软预算；达到后暂停自动分析并提示作者继续、调整频率或结束会话；
- 作者主动发起的定向检查始终可用，但系统继续显示已发生的分析次数；
- 低频、高频和手动模式作为可切换设置保留。

字符阈值、时间和预算都是可配置默认值，不用于限制作者主动请求检查。

### 24.5 数据方案

确认采用第 16.5～16.8 节的混合数据方案：重要作品事实和结构化事件随 Git 仓库迁移；本机数据库只承担可重建索引与临时运行状态；恢复快照位于仓库外；作者级长期档案独立导入导出。

### 24.6 Git stage

- Agent 不自行 stage 或 unstage；
- 作者明确说“提交这些改动”时，该指令同时授权暂存本次提交范围内的相关文件并创建提交；
- 该授权不包括无关文件，也不自动包含 push；
- 若提交范围存在歧义，先展示建议文件清单并等待作者确认。

### 24.7 联网检索

- 默认按任务/会话授权，不给予永久全局联网权限；
- Researcher 可以在任务开始时一次申请该任务所需的联网范围，任务结束后授权失效；
- Writer、Observer 等角色不会因 Researcher 获得授权而自动获得联网权限；
- 连接作者主动选择的通用 Agent 属于基础运行条件；把未公开正文发送给新的第三方服务仍需单独确认。

### 24.8 正典自动化边界

- 修改、删除或覆盖作者已确认的核心正典，必须由作者确认；
- 正文已经明确写出的低风险状态变化，可以自动记录为“正文明确出现”，并关联章节和原文证据；
- 自动提取不能把条目升级成“作者已确认”，也不能静默覆盖已有事实；
- 与现有正典冲突或可能构成追溯修改时，只生成候选和影响分析，等待作者决定。

### 24.9 创作导航默认模式

- 默认引导强度：陪跑模式；
- 默认规划方式：滚动规划；
- 规划视野：保留全书方向和结局假设，维护当前卷骨架，详细规划未来一至三章；
- 首次使用不以长问卷阻塞写作，系统先生成建议并只询问高影响决定；
- 作者可以随时切换到教学、自由、大纲、探索或托管模式。

### 24.10 基线状态

V0.2 已无悬而未决的产品默认项。尚未展开的字段级数据结构、适配器消息格式和具体页面交互属于下一阶段设计文档，不得借实现细节反向改变本需求基线。

## 27. 2026-08-24 作者可用性补充基线

以下内容来自作者对真实运行界面的直接验收纠正，优先于此前以功能数量为中心的完成性判断，状态均为 **[已确认]**：

1. **项目与内容生命周期**：打开任何作品后仍可新建小说；平台显示当前仓库绝对路径、Finder 入口、分支、HEAD 与 remote。所有作者可创建的仓库内容——正文章节/分卷、大纲与剧情、研究资料、人物与世界/正典、已确认决定、这些区域的嵌套目录，以及系列仓库中的单部作品——都必须具备影响预览、明确确认、仓库外回收站和原位置恢复；内容区域根目录和系列最后一部作品受保护。整个仓库只移入系统废纸篓。任务、评论、故事事实、剧情候选和 Agent 会话等只追加结构化记录不得物理抹除历史，分别使用取消、拒绝/作废、废弃/恢复和停止等状态语义。
2. **人类可读 Git**：Git 变更不得默认展示裸 patch 或整行 JSON；正文使用成熟 diff 组件提供行号、增删色、split/unified 和上下文，系统事件先翻译为作者可读摘要，同时保留原始审计入口。
3. **风格 CRUD**：长期实写必须形成可见的多证据风格候选；风格规则支持查看证据、确认、拒绝、编辑和删除，并同步作者档案与仓库快照。
4. **信息架构去重**：评论、Agent 和上下文统一位于右侧辅助面板；左侧不再设置点击后只显示“功能在右侧”的重复空页面。
5. **用户文档与引导**：提供从一句灵感开始的首次引导、页面内帮助和面向非技术作者的完整指南，解释 Git、Agent、Observer、删除、恢复与换电脑。
6. **全局视觉门禁**：普通文字对比度至少 4.5:1，大字号至少 3:1；全页面和关键弹窗必须做运行时扫描及真实 Electron 截图回归，不能只修作者指出的局部截图。
7. **完成性判断**：功能矩阵全绿、测试通过和构建通过都不是平台完成的充分条件；生命周期、可读性、风格 CRUD、引导和全页面 UI 五个维度均通过真实作者路径后，才可再次判断完成。
